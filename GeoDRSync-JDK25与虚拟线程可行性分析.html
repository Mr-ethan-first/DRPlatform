GeoDRSync — JDK 25 升级 & 虚拟线程可行性分析

针对灾备同步引擎（Flink CDC 2.2.0 / flink-cdc 3.7.0-2.2 / Spring Boot 3.4.3）的评估 · 评估日期 2026-10-18

一、总结论（先给结论）

不可行
升级到 JDK 25
Flink 2.2.0 官方仅支持 Java 11 / 17 / 21；MiniCluster 与应用同进程同 JVM，无法拆分。JDK 25 属未测试组合，风险极高、收益为零。
不适用
改用虚拟线程
虚拟线程自 JDK 21 已 GA，当前运行时（JDK 21）已原生支持；但一致性关键路径是 Flink sink 的 checkpoint 屏障对齐，虚拟线程无法安全套用，且在真正的热路径上无显著收益。
决策：用户原话的条件是「如果可行并且能显著提升性能，则升级 + 改虚拟线程」。经分析，两个条件均不成立—— JDK 25 对当前 Flink 栈不可行；虚拟线程既不能安全应用到一致性关键路径、也无法显著提升吞吐。 因此不执行升级、不改动线程模型，并给出零一致性风险的安全性能杠杆（见第五节）。

二、升级到 JDK 25 的可行性

维度结论与依据
Flink 2.2.0 官方支持矩阵 硬阻塞 Flink 2.2 的 Java 支持范围为 11 / 17 / 21（Confluent 支持矩阵、Flink Doris Connector 文档均确认；Flink 2.2 字节码以 --release 17 编译）。JDK 25 不在支持范围。
嵌入式运行约束 本工程 StreamExecutionEnvironment.createLocalEnvironment()（FlinkCdcSyncJob.java:144）把 Flink MiniCluster 跑在应用同一进程、同一 JVM 内。无法做到「Spring Boot 跑 JDK 25、Flink 跑 JDK 21」的拆分。
Spring Boot 3.4.3 支持范围 临界 官方声明上限 Java 24；JDK 25 也超出其声明的支持范围，即便撇开 Flink，Web 层也落在未测试区。
机器上是否已有 JDK 25 是：/d/software/jdk-25.0.2 已安装，且当前 PATH 默认 java -version 已返回 25.0.2。应用按约定显式用 /d/software/jdk-21.0.11 启动（见 memory）。风险提示：一旦启动脚本忘记钉死 JDK 21，就会落到未支持的 JDK 25，需排查。
若强行升级 Flink 以支持 25 等于把 Flink 升到支持 JDK 25 的新大版本，且 flink-cdc 3.7.0-2.2 绑定 Flink 2.2 需配套升级——一次重大迁移，会直接冲击我们刚验证过的一致性逻辑（双 shaded-guava、savepoint 恢复、屏障对齐），收益为零（虚拟线程不需要 25）。

三、虚拟线程能否提升性能

3.1 一个必须先澄清的前提

虚拟线程（Project Loom）自 JDK 21 起 GA。本工程运行时就是 JDK 21，已经可以原生使用虚拟线程。因此「为用虚拟线程而升级到 JDK 25」本身是个伪前提——要不要用虚拟线程与 JDK 25 无关。

3.2 一致性关键路径 = Flink Sink，虚拟线程无法安全套用

真正的写入发生在 IdempotentMySqlSink（RichSinkFunction），其一致性保证完全依赖单线程 + checkpoint 屏障同步 flush：

  • invoke() 跑在 Flink 算子线程（每 subtask 单线程），缓冲 LinkedHashMap 仅被单线程访问。
  • snapshotState()（checkpoint 屏障）调用 flushAll() 同步落库后屏障才通过——这是 Exactly-Once 的命门。
  • keyBy(tableKey) 保证同表进同一 subtask → 顺序保序；DDL 前先 flush 同 subtask 全部数据保结构/数据相对顺序。
  • 若并行化写：缓冲变共享需加锁；checkpoint flush 必须等所有 VT 完成。任何「屏障越过未落库数据」的瞬间都会破坏一致性，与用户「不能丢、不能重」的硬约束直接冲突。

3.3 瓶颈本就不是「线程数」

吞吐 / 延迟决定因素说明
MySQL I/O 带宽sink 落库是 JDBC 写，受目标库磁盘/网络/锁主导。加线程不会线性放大写带宽，反而增加行锁/间隙锁竞争。
Flink 并行度 parallelism按表分片，多 subtask=多并行写流。已是可配杠杆（cfg.getParallelism() / application.yml）。
批大小 sinkBatchSize当前按批落库，调大单批可摊薄网络往返。
checkpoint 间隔（≈3s）实测实时延迟 p50≈2.4s、p99≈3.7s 几乎全部由 3s checkpoint 间隔决定，不是线程阻塞。降间隔才降延迟。

结论：虚拟线程解决的是「海量阻塞任务抢 OS 线程」的扩展性问题；本设计刻意按 subtask 串行以保序 + 对齐屏障，加线程既不会线性提升 MySQL 写带宽，又要为一致性付出巨大且危险的重构成本。在热路径上无显著收益。

3.4 应用层编排（非热路径）

DatabaseSyncManager / FlinkCdcJobManager / watchdog / 旧轮询引擎（SyncHostJob、GroupedExecutorManager）并发度极低、不是吞吐瓶颈；且旧轮询引擎在 CDC 模式下根本不运行。改写为虚拟线程纯属改动成本，无收益。

四、为什么「升级 + 虚拟线程」整体不可取

  • JDK 25 不可行：Flink 2.2.0 仅支持 11/17/21，MiniCluster 与应用同 JVM；要兼容 25 须同步做大版本迁移，冲击已验证一致性逻辑。
  • 虚拟线程不必要：JDK 21 已原生支持，与 25 无关。
  • 虚拟线程不安全：一致性关键路径是 Flink sink 的屏障对齐 flush，并行写会破坏 Exactly-Once。
  • 虚拟线程不显著：真正瓶颈是 I/O 并行度与 checkpoint 间隔，加线程无线性收益。

⇒ 用户条件「可行 且 显著提升性能」两项均不满足，不执行升级、不改虚拟线程，以严格守住「不丢、不重」底线。

五、零一致性风险的安全性能杠杆（建议，未执行）

杠杆风险作用与位置
提高 Flink parallelism安全多 subtask → 更多并行写流；表数量多时收益明显。配置：application.yml drplatform.cdc.parallelism。
提高 sinkBatchSize / sourceConnectionPoolSize / sink poolSize安全提高单批吞吐、放宽源/目标连接数。配置：application.yml drplatform.cdc.*。
调小 checkpoint 间隔（当前 3s）权衡降实时延迟但增 checkpoint 开销；过小反而拖累吞吐。需压测取平衡。
放宽目标库连接上限安全DynamicShardedConnectionManager 的 maxGlobalConnections 与目标 MySQL max_connections 需匹配，避免被信号量饿死。
（唯一安全且有益的 VT 落点）alignSourceAutoIncrement 并行化安全切换期批量 SELECT MAX+ALTER 属维护操作、非数据热路径、失败可降级；可用虚拟线程并行扫描多表。收益有限、非用户诉求的「处理能力」。
