测试口径说明： 全量同步速度 来自 2026-10-17 的 45 库大规模压测（perflab profile，同一 Docker 引擎、同一份代码）； 实时同步时效性 来自 2026-10-18 的端到端延迟基准（默认 profile，geo_source.t_order）； 增量风暴 来自 2026-10-17 的补测。三者均为真实运行数据，非理论估算。 全量速率按 information_schema 行数近似值计算；延迟为「源库事务提交 → 目标库可见」的端到端墙钟时间。
指标辨析（两组数字为什么不一样）： ~3029 行/s 是 45 库小表规模化场景的端到端平均——含每库作业启动、schema 快照、checkpoint 协调、DDL 传播等机制开销；平均每表仅 ~520 行，作业未跑热即结束，故由机制开销主导。 2.3–2.7 万行/s 是单表 20 万行的纯搬运吞吐——快照切 25 个 split 并行导出、无重启开销，代表数据移动本身的上限。表越小端到端平均越接近机制开销极限，表越大越接近吞吐上限，两个数字分别回答「多小表规模化」与「大表极限性能」，不可互相替代。 实时延迟 p99 3.7s 为持续写入负载下的 p99 分位（事件排队等 checkpoint barrier / 满批 flush，ckpt=3s）； 增量延时 ~1.0s 为稀疏单行在近空闲状态的平均可见时延（ckpt=1s）。二者差异来自统计量（p99 vs avg）、负载（忙时排队 vs 闲时直达）与 ckpt 配置（3s vs 1s）。

四、为什么实时延迟稳定在 ~3s（机理说明）

GeoDRSync 采用 Flink CDC 的 快照 + 增量 两阶段管道，实时延迟的下界由 checkpoint 机制决定：

  • Checkpoint 屏障对齐（EXACTLY_ONCE）：作业每 3s 触发一次 checkpoint；sink 在收到 barrier 前先同步 flush 已缓冲的变更，位点不越过任何未落库的数据。因此单条变更的「可见时刻」= 它被纳入的下一个 checkpoint 完成时刻，典型延迟即落在 0–3s 区间。
  • 同表保序（keyBy）：按 库.表 分区，同表变更严格有序，避免乱序导致的临时不一致。
  • DDL 与行同键、先 flush 再改结构：DDL 事件与同表的行变更走同一 key，sink 先 flush 已有行、再应用结构变更，杜绝「结构未变就写新列」的报错。
  • 落库幂等：写入用 INSERT … ON DUPLICATE KEY UPDATE，删除用 NULL-safe 比对；即使 checkpoint 重放也不会产生重复或丢失。
  • 批量聚合：一个 checkpoint 周期内到达的多条变更会被聚合后批量写入，故「突发写入」与「单条写入」延迟接近，p99 不明显抬升。

六、运行时动态配置与硬件缩放实证（2026-10-18 补充）

本节为报告发布后的补充实测：引擎已支持 13 项运行时参数热调（GET/POST /sync/runtime-config， apply=true 时经 savepoint 无损切换、零丢数据），并行度可显式配置或按 CPU 自动适配（0=auto，1–64）。 以下实验量化「调参数」与「换硬件」各自能带来多少收益，全部为真实运行数据。

实验环境：本机 6 核 12 线程 / 15.9G 内存（源/目标 MySQL 与本服务同机 Docker）， 应用自动并行度=12（已超售物理核）。因此本节「参数旋钮」收益为实测值；「24 核 + 16G/32G」为基于瓶颈定位的外推预估， 部署到 24 核实机后可用 tests/bench_big.py 复测校准。

6.4 升级到 24 核 + 16G/32G 堆的收益预估

场景当前（12 核实测）24 核 + 大堆预估依据
增量单行延时3.0 s~1.0 sckpt=1s 实测，与硬件无关
增量积压消化吞吐2.3 万行/s4–6 万行/s（~2×）外推：24 真实核 + batch 2000–4000 + pool 4–8
大表全量（100 万行）~43 s 落库~20 s同上外推
小表全量（≤10 万行）~15 s不变机制开销主导，实测验证
多库多表翻倍场景splits>12 时需分波次~2×splits = 表数×chunk 数 ≥24 时一波完成；chunk 需调小至 2000–4000
堆内存的角色是「使能项」而非直接提速：16G/32G 堆允许 TaskManager 开到 4–8G—— 高并行度下 network/managed 内存不被反压掐住、大批次 buffer 不 OOM、G1 停顿占比下降使 1s checkpoint 的 barrier 更稳； JVM 启动需 -Xmx > TM 内存 + 2G 余量。所有场景的硬天花板是目标 MySQL 单实例写入能力， 若目标库不同步升级，提升将止步于目标库上限——那种情况应优先升级目标库或按库分治到多个目标实例。
