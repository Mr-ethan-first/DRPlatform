同步方向：生产主库(13306) → GeoDRSync → 灾备库(13307)；备源(13308)是主库的实时副本，主库故障时可切换为源。灾备库经 /sync/mapping/reverse 可整体反向成为新生产中心。

二、最终一致性的总体保证

本系统以 Flink CDC 的 checkpoint 屏障对齐 为基石，配合 幂等写入（upsert / NULL-safe delete）、同表 keyBy 保序、DDL 与行事件同键并先 flush 再改结构、以及 恢复路径优先级（savepoint > retained checkpoint > INITIAL 兜底），在 DML / DDL / 断电 / 断网 / 主备切换 / 方向反转 各类场景下实现 不丢、不重、最终一致。

一句话恢复优先级： 显式 savepoint（元库记录） → retained checkpoint（RETAIN_ON_CANCELLATION 保留） → INITIAL 全量重扫兜底。checkpoint 目录按 chk-N 数值排序选取最新位点（修复过字符串排序把 chk-9 排到 chk-45 之后选旧位点的 bug）。

三、DML（INSERT / UPDATE / DELETE）一致性

1. 捕获与解析

  • MySqlSource 以 StartupOptions.initial() 启动：先整库快照（事件 op=r），快照结束无缝衔接 binlog 增量（c/u/d）。
  • JsonToCdcEventFunction 把 Debezium JSON 解析为 CdcEvent(before / after / op / source.ts_ms)，作为后续所有语义的输入。

2. 写入语义（幂等核心）

操作落库语句幂等性说明
写 / 更新 / 快照INSERT ... ON DUPLICATE KEY UPDATE按整行 after 做 upsert；重放同一行无副作用（覆盖自身）。
删除DELETE FROM t WHERE (before 列 <=> ?) OR ...用 before 镜像 + NULL-safe 等值（<=>）匹配，无需主键知识；删不存在的行无副作用。

3. 顺序与屏障对齐（不丢不重的关键）

  • 同表保序：keyBy(tableKey) 把同一 库.表 的全部行事件 + DDL 路由到同一 subtask，严格保持 binlog 相对顺序。
  • DDL 与行同键：sink 处理 DDL 前先 flushAll() 落盘该 subtask 全部待写数据，再执行结构变更 —— 保证「结构变更前的所有数据已落地，再改结构」。
  • checkpoint 屏障对齐（EXACTLY_ONCE）：snapshotState() 在 checkpoint 屏障到达时同步 flush 全部缓冲，屏障在「上游事件已全部处理且落库」后才通过 → 已确认的 binlog 位点永不越过未落库数据。崩溃后从 checkpoint 位点重放，upsert/delete 幂等 → 不丢不重。
  • 延迟监控：CdcLagRegistry 统计 source.ts_ms 与落库时间差，超过 lagWarnSeconds=10s 告警。

四、DDL（CREATE / DROP / ALTER / TRUNCATE / RENAME）一致性

1. 捕获

  • includeSchemaChanges=true。快照阶段 DDL 在顶层 ddl 字段；binlog 阶段 schema-change 事件的 DDL 藏在 historyRecord（JSON-in-string） → unwrapHistoryRecord 解包回填 ddl/databaseName。
  • extractTable 从 DDL 文本提取表名作为 keyBy 键，保证 DDL 与同行数据同序。

2. 应用与清洗（DdlApplier）

清洗规则目的
去除库限定符 `db`.目标端按当前库执行（源/目标库名不同也能套用）。
utf8mb4_0900_* → utf8mb4_general_ci源 8.0 专有排序规则，目标 5.7 不认 → 降级可移植。
CREATE TABLE/DB 补 IF NOT EXISTSsavepoint 恢复重放 DDL 时幂等。
跳过 USE/SET/FLUSH/SAVEPOINT/事务类会话语句会话级语句不同步到目标。

3. 幂等重放

恢复时位点前后的 DDL 会被重放一次，目标已生效的结构变更会报「已存在/不存在」类错误，按成功处理跳过：1050(表已存在) / 1007(库已存在) / 1060(列重复) / 1061(键名重复) / 1091(列不存在，DROP)。

4. 目标库 / 表懒创建

  • 新增库：sink ensureTargetDatabase 自动 CREATE DATABASE IF NOT EXISTS（修复「目标库不存在 → 作业 FAILED 耗尽重启」）。
  • 新增表：ensureTargetTable 查 information_schema，缺失则从源 SHOW CREATE TABLE 经 DdlApplier.sanitize 后建表。

5. 动态新增库/表发现（运行期）

flink-cdc 的 scanNewlyAddedTable 只在作业 open()/恢复时探测一次，运行期不自动发现。由 FlinkCdcJobManager.watchdog 周期（discoveryIntervalSec=20s）扫描源库与基线 capturedTables 对比，发现新增后打 savepoint → 重启纳入。两个关键修正：

  • 基线在 job.start() 之后立即取，否则「启动瞬间新建的表」被误记基线而永不发现；
  • 基线只在重启真正成功后更新，否则被冷却期（discoveryRestartCooldownSec=60s）跳过的发现会永久丢失。

6. 目标端缺表补齐

watchdog 对比目标端，源有目标无：空表 tryCreateEmptyTable 直接复制建表（CDC 不产生行事件不会建）；非空表（首轮全量中途崩溃）触发 forceInitial 全量重扫，重试上限 3 次 防重启风暴。

7. TRUNCATE / RENAME / 字段转换

  • TRUNCATE：作为 DDL 重放，目标执行 truncate 清空（与目标数据一致）。
  • RENAME：CDC 中以 drop+create 组合出现，目标端按新建表同步；旧表若保留为独立表则各自同步。
  • 字段转换：TransformRule（db/table 支持 * 通配，仅非主键列、字符串等值）在 sink applyTransforms 对 after/before 应用 → 源库原值不变，目标库写转换值（例 secret→MASKED）。只改非主键，避免破坏 upsert 幂等键。

五、断电场景一致性

1. 应用进程强杀（kill -9 / 宕机）

  • 重启后 FlinkCdcJobManager 按优先级恢复：显式 savepoint（元库 cdc_job_state）→ retained checkpoint（RETAIN_ON_CANCELLATION 保留）→ INITIAL 全量兜底。
  • 恢复路径失效（checkpoint 损坏/被删）→ startInternal 退化为 INITIAL 全量重扫（代价一次全量，优于彻底停同步）。
  • 角色持久化：换源/换向后写入 geodrsync-dynamic-mappings.json，重启后新方向优先于 yml 生效，防止「故障切换被静默回滚」。
  • 优雅停机 @PreDestroy：对所有作业 stopWithSavepoint（落安全点再停）。

2. 目标库断电（docker stop / 宕机）

  • sink 写目标失败 → Flink 固定延迟重启策略（attempts=20, delay=5s）自愈；耗尽 → watchdog 拉起作业。
  • 恢复后从最近 checkpoint 位点续传（不会重全量），upsert/delete 幂等 → 行数精确一致（实测 18/18、28/28 收敛）。

3. 源库断电

CDC 源连接中断 → MySqlSource 内部重连（connectMaxRetries=3）；binlog 位点不前进，恢复后从原位点续读，不丢数据。

六、断网场景一致性

网络分区/断网本质 = 管道中断，与断电走同一套重连 / 重启 / 续传机制：

断网位置表现一致性保证
源库断网（pause）源不可达，source 暂停拉取，位点不变恢复后从断点续读（实测源断网 25s 恢复，新增 5 行 5s 到达，全库一致）
目标库断网（pause）sink 写失败Flink 重启 + watchdog 拉起，恢复后续传，行数精确一致
应用↔元库 / 目标跨网络断同目标断电处理作业拉起后从 checkpoint 续传
运维注意：本系统同步在单机 Docker 多端口；跨机房断网即对应「源或目标主机不可达」，由上述机制兜底。测试/运维通过 curl --noproxy "*" / requests(trust_env=False) 访问，避免本地代理把 127.0.0.1 误发代理（已踩坑：代理返回 502 被误判为服务未就绪）。

七、主备切换 / 方向反转（failover & failback）一致性

1. 主备切换 switchSourceToStandby（同中心 主↔备）

  1. 停旧作业 → 释放旧源连接池（必须用旧 instanceKey 停，换源后 key 含端口会变）；
  2. 源↔备源地址交换（可反复来回切换）；
  3. 主键对齐；
  4. 新源以 INITIAL 全量重扫（换源后旧 binlog 位点作废，绝不可用 startOrResume 用旧位点续读，否则漏数据或 FAILED）。

2. 方向反转 reverseDirection（灾备↔生产）

  • 交换 source ↔ target（含 user/password），备源地址不变（挂在源侧）→ 调用两次必然回到初始状态（可逆）。
  • 用 onSourceSwitched → INITIAL 全量重扫；方向持久化 geodrsync-dynamic-mappings.json（重启不回退）。
  • 典型：灾备切生产（failover） / 生产切灾备（failback）。

3. 主键对齐 alignSourceAutoIncrement（防真实丢失的关键）

新源 AUTO_INCREMENT 必须 > 目标端已存在主键 MAX。否则新写入复用旧 id，upsert 按主键覆盖「不同业务行」→ 真实数据丢失。实现：对每个单列主键表比较 目标 MAX(pk) 与 新源 MAX(pk)，若新源落后则 ALTER TABLE ... AUTO_INCREMENT = 目标MAX+1（只改元数据、不锁行）。由 ha.auto-align-source-autoincrement=true 控制（默认开）。

4. 切换前后数据一致性判定口径

切换是「灾备 ⊇ 备源」的超集关系：备库只到克隆/切换时刻，灾备目标还保留主库故障前的尾部写入；CDC 不做删除对账 → 切回主源后灾备比生产多出的故障期写入是正确保留，不是数据丢失。验证脚本用 wait_superset 而非 identical 判定（反向 < 才代表真实丢失）。切换前后数据不丢：切前源行数在目标端完整保留（实测 31→37 等）。
